## Context

PRD section 9.7 requires transferable binary buffers for assembly/PDB/asset transfer per `src/shared/Protocol.md` (issue 15). Section 13.1 describes the runner loading the compiled assembly and inspecting its types. Critical feasibility question 9 (section 19) asks whether the generated DLL and PDB can be loaded dynamically. This issue connects the compiler (issue 17/19) and the preview (issue 20) for the first time: it sends the DLL+PDB bytes produced by `CompilationService.Compile` from the top-level frontend into the preview iframe as `preview.load.request` using the protocol envelope from issue 15, and loads them with `System.Reflection.Assembly.Load` inside the preview's .NET runtime, proving the assembly and its debug symbols are both present and loadable — without yet discovering/running a `Game` subclass (that is issue 22).

## What to build

Implement the message flow: compiler produces DLL+PDB bytes (issue 17) → top-level frontend receives them and forwards them to the preview iframe as a `preview.load` message using the transferable-buffer binary representation defined in `src/shared/Protocol.md` (issue 15) → preview's `PreviewExports` receives the bytes and calls `Assembly.Load(dllBytes, pdbBytes)`, confirming the loaded assembly's `FullName` and that PDB sequence points are present (e.g. via `System.Diagnostics.StackTrace` symbol resolution or `System.Reflection.Metadata` PDB inspection).

## Scope

### In scope

- Extending `PreviewExports.cs` with `[JSExport] public static string LoadUserAssembly(byte[] dllBytes, byte[] pdbBytes)` (or the JS-interop-compatible equivalent signature for byte array marshaling in this SDK version)
- Frontend code that receives the compiler's output over a private compiler `MessagePort` and forwards it over a separate private preview `MessagePort` with a transfer list, following the exact `compile.response`, `preview.load.request`, and `preview.load.response` shapes from `src/shared/Protocol.md`
- Confirming the loaded assembly exposes PDB-backed line information (a minimal proof, not yet the full exception-mapping feature of issue 29)

### Out of scope

- Discovering/instantiating a `Game` subclass (issue 22)
- Running the game loop (issue 23)
- Full exception-to-source-line mapping (issue 29, which builds on this)

## Implementation guidance

1. In `src/preview/PreviewExports.cs`, add:
```csharp
[JSExport]
public static string LoadUserAssembly(byte[] dllBytes, byte[] pdbBytes)
{
    var asm = System.Reflection.Assembly.Load(dllBytes, pdbBytes);
    return asm.FullName ?? "<unknown>";
}
```
2. Confirm the marshaling of `byte[]` parameters is supported by the current `System.Runtime.InteropServices.JavaScript` `[JSExport]` attribute in this SDK version (check `dotnet --version` compatibility; if raw `byte[]` marshaling is unsupported for `[JSExport]` in this SDK, use the documented workaround of passing a JS `Uint8Array`/`ArrayBuffer` argument typed as `byte[]` per the JS interop docs, or stage the bytes via a JS-side shared buffer and a `[JSImport]` callback — inspect actual .NET 8/9 browser interop docs for the exact supported marshaling method in the installed SDK).
3. Bootstrap each context with exactly one `window.postMessage` addressed to its exact `contentWindow`, transferring a fresh private `MessagePort`. After bootstrap, construct the `preview.load.request` envelope from `src/shared/Protocol.md` and call the preview port's `postMessage(envelope, [dllBuffer, pdbBuffer])`.
4. Inside the preview iframe's JS boot script, accept only that one bootstrap window message. Validate subsequent port messages, including `protocolVersion` and `type === "preview.load.request"`, before extracting the transferred buffers and calling `LoadUserAssembly`; return `preview.load.response` on the same port.
5. Prove PDB presence: after `Assembly.Load`, use `new System.Diagnostics.StackTrace(true)` inside a deliberately-thrown-and-caught exception in a temporary test method within the loaded assembly, or inspect the assembly's embedded/companion PDB via `System.Reflection.Metadata.MetadataReaderProvider.FromPortablePdbStream` and confirm at least one sequence point exists mapping to the original source file name used in issue 17/18's compilation input.
6. Use the trivial `Foo` class compiled in issue 17/18 as the test payload for this issue's proof.
