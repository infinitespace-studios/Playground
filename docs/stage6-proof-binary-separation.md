### Could it be fewer than eight? (explicitly considered)

Yes — three consolidations are *possible* but **not recommended** for Stage 6:

- `workspace_save_dialog` + `workspace_open_dialog` + `project_pick_folder`
  could merge into one `workspace_file_dialog(mode)` command (3→1).
- `first_run_check_acknowledgement` + `first_run_write_acknowledgement` could
  merge into `first_run_acknowledgement(op)` (2→1).

That would reach **five** product commands. **Recommendation: keep eight
one-for-one.** Each current command is a distinct native capability with its own
argument/return shape and its own least-privilege ACL grant; collapsing them
behind a `mode`/`op` discriminator widens each grant's blast radius (one ACL
entry now authorizes save *and* open *and* folder-pick) for no product benefit,
and it would be a behavioral change layered on top of a rename during the same
stage. Eight cleanly-named, single-responsibility commands satisfy the plan's
"approximately eight domain-named PRODUCT commands" target directly. The rename
is behavior-preserving; consolidation is deferred (Stage 7 candidate, if ever).

### Migration / compatibility strategy

1. **PRODUCT rename is a hard cutover, not an alias.** Rename the eight handlers,
   their statics/consts/helpers, the three product frontend callers, the
   `APP_COMMANDS`/`main.toml`/autogenerated ACL entries, and regenerate the
   per-command permission files. No compatibility shim in the product binary —
   old names must not exist there (enforced by the artifact checks in (e)).
2. **Proof-side compatibility is confined to the proof harness.** The two
   `first_run_*` acknowledgement commands are called by both the product
   (`first-run-warning.ts`) and the proof suite (`proof-project-lifecycle.ts`
   two-phase proof). The renamed commands are the single source of truth; the
   proof suite calls the **new** names. Any packaged proof shell script
   (`prove-scenarios-macos.sh`, `prove-issue037-macos.sh`) that greps report keys
   keeps its `ISSUE0xx_REPORT=`/env-gate contract because those live on the
   *proof* commands, which move behind the feature (see (c)/(d)); the product
   rename does not touch report keys.
3. **`ISSUE034_APPROVED_COMMANDS` becomes two lists.** Today it is the single
   82-entry inventory scanned by `build.rs`. After the split it must reflect the
   default (product, 8) inventory when built without the feature and the full
   (product + proof) inventory when built with the feature — see (d) for the
   exact wiring. The frontend security scenario that owns this list is proof-only
   and thus present only in the proof build.
4. **Two build-time inventory constants.** `build.rs` gains `PRODUCT_COMMANDS`
   (8, always) and `PROOF_COMMANDS` (74, feature-gated). `APP_COMMANDS` becomes
   the concatenation actually compiled (8 without the feature, 82 with it). All
   ACL/handler drift assertions bind against the correct list per profile.

## (d) Recommended proof boundary and exact build wiring

### Recommendation: non-default `proof-harness` Cargo feature (not a separate crate)

**Rationale.** The proof commands are deeply interleaved with the single app
shell: they share the one `tauri::Builder`, the one `generate_handler!` (build.rs
asserts *exactly one* `invoke_handler` and one `generate_handler!`), the
`playground-preview` protocol closure, the `run()`/`setup` lifecycle, the
LaunchServices relay, and the macOS AppKit activation. A separate proof crate
would have to duplicate the entire Tauri shell (window creation, protocol, menu,
dialog plugin, CSP) or expose the builder across a crate boundary — large,
error-prone, and it would fork the product's own security-critical setup. A
**non-default feature** keeps one shell and compiles the proof surface in/out with
`#[cfg(feature = "proof-harness")]`, which is exactly the plan's first option and
the minimal durable boundary.

### Cargo.toml

```toml
[features]
default = []
proof-harness = []
```

`build.rs::validate_cargo_manifest` must be extended to accept the new
`[features]` root section (add `"features"` to the approved root-keys list and
assert its exact contents), keeping its existing negative fixtures.

### lib.rs

- Annotate every proof command fn, proof helper, proof static/type, the
  `relay_packaged_proof_through_launch_services()` call in `run()`, the
  `packaged_pipeline_proof_enabled()` block in `.setup()`, and the
  `issue039_handle_asset_transfer_get` protocol branch with
  `#[cfg(feature = "proof-harness")]`.
- The `generate_handler!` macro must list product commands always and proof
  commands only under the feature. Because `generate_handler!` is a single macro
  invocation (build.rs asserts count == 1), use `cfg!`-gated inclusion via a
  small compile-time list or `#[cfg_attr]`-style conditional entries. Concretely:
  keep one macro call; wrap the proof command identifiers with per-line
  `#[cfg(feature = "proof-harness")]` (supported inside `generate_handler!` as
  it expands normal token trees), or build the handler from a `cfg`-selected
  module. The eight product commands are unconditional.

### build.rs

```
const PRODUCT_COMMANDS: &[&str] = &[ 8 renamed product commands ];
#[cfg(feature = "proof-harness")]  // build script sees the feature via CARGO_FEATURE_PROOF_HARNESS
const PROOF_COMMANDS: &[&str] = &[ 74 proof+dead commands ];
```

- Detect the feature in `build.rs` with
  `std::env::var_os("CARGO_FEATURE_PROOF_HARNESS")`.
- `APP_COMMANDS` (the effective inventory the ACL/handler drift checks bind
  against) = `PRODUCT_COMMANDS` when the feature is off, `PRODUCT_COMMANDS ++
  PROOF_COMMANDS` when on.
- `validate_generated_acl` asserts `1 + 1 + APP_COMMANDS.len()` equals **10**
  (product) or **84** (proof).
- `main.toml` / `capabilities/main.json` / autogenerated permissions must be
  generated/validated per profile. Simplest durable approach: **two committed
  permission inventories** — `permissions/main.toml` holds the 8 product commands;
  a proof overlay (only compiled/validated under the feature) holds the 74. The
  autogenerated dir must contain exactly 10 or 84 files accordingly.
  `tauri_build::AppManifest::new().commands(APP_COMMANDS)` receives the
  profile-correct list.
- `validate_frontend_command_inventory` runs only under the feature (the
  `proof-preview-security.ts` inventory ships only in the proof frontend). When
  the feature is off, skip that scan.

### tauri.conf.json / tauri.proof.conf.json / package.json

- Product build (`npm --prefix src/desktop run tauri -- build`, release CI) →
  default features → 8 commands, no proof code.
- Proof build must pass `--features proof-harness` to Cargo. Tauri v2 does not
  put Cargo features in `tauri.conf.json`; thread the feature through the build
  invocation. Options (pick one, document it):
  1. `tauri build --config src-tauri/tauri.proof.conf.json -- --features proof-harness`
     (args after `--` go to Cargo), wired into `src/desktop` `package.json`
     `tauri:proof` script and `prove-scenarios-macos.sh` / `measure-performance`.
  2. A `[env]`/wrapper that sets the feature for the proof leg only.
- Release CI (`.github/workflows/release.yml`) already builds PRODUCT
  (`beforeBuildCommand: npm … run build`, then `check:profile-product`). It must
  **not** pass the feature. Stage 6 adds a CI assertion that the product bundle
  exposes only the 8 product commands (see (e)).

### Net effect

- Normal npm/Tauri/release binary: 8 product commands, effective ACL 10, zero
  proof commands/state/markers, no LaunchServices relay, no AppKit proof
  activation, no asset-transfer protocol branch.
- Proof binary (`--features proof-harness` + `dist-proof` + proof identifier):
  82 commands, effective ACL 84, all scenario capabilities retained.

## (e) Binary / runtime artifact enforcement (non-vacuous)

Product-frontend module-graph and marker checks already exist
(`check-profile-artifacts.mjs`). Stage 6 adds **binary/runtime** checks that read
the *compiled* artifacts, with anti-vacuity guards so a broken scan fails loudly.

1. **PRODUCT binary exposes only the 8 product commands.** Parse the release
   binary's ACL/handler evidence and assert:
   - the 8 renamed product command strings are **present** (positive floor — the
     scan cannot pass on an empty/failed read);
   - **none** of the 74 proof/dead command strings (and no `issue0`-prefixed
     command token) is present.
   Source of truth: `tauri_build` bakes the command list into
   `gen/schemas/acl-manifests.json` / `capabilities.json`. The check reads the
   generated ACL manifest from the product build and diffs it against
   `PRODUCT_COMMANDS`. Reinforce with a raw `strings`/byte scan of the release
   executable for a known proof-only symbol (e.g. `issue040_dispatch_preview_input`,
   `MONOGAME_ISSUE034_PROOF`, `MONOGAME_PROOF_REPORT_RELAY`) → must be **absent**;
   and for a product symbol (`workspace_write_file`) → must be **present**. The
   present/absent pairing defeats vacuous "found nothing because I scanned the
   wrong file" passes.
2. **PROOF binary retains scenario capabilities.** The same tool, run against the
   proof binary, asserts all 82 commands present and the proof symbols
   (`issue040_dispatch_preview_input`, `ISSUE040_REPORT`) present — proving the
   feature actually compiled the harness in.
3. **Effective-ACL count assertion per profile** (already in `build.rs`, retuned):
   product `10`, proof `84`. A drifted inventory fails the build.
4. **Product-staged preview asset scan.** Extend `build.rs`'s existing
   canary/size scan of `src/frontend/dist` to assert the product-embedded
   `preview.js` / preview runtime contains **no** proof-only export names
   (`QueryIssue039State`, `QueryIssue040AudioState`, `QueryStoppedGameProof`,
   `installIssue040AudioProbe`, `previewIssue*Proof`, `initializeCompilerProofMode`).
   Non-vacuous: also assert a **product** export (`MountContentAssets`,
   `CommitMount`) **is** present, so the scan proves it read a real preview asset.
5. **Feature-off compile guard.** A `cargo check` (default features) must compile

6. **`check:profile-product`** (unchanged) proves the product **frontend** graph

   **backend** has zero proof commands/state. Together they close the loop the

## Must anything remain larger than eight product commands? — justification

**No product command must exceed eight, and eight is the recommended target.**
The eight fall into three least-privilege responsibilities:

- **Workspace file I/O (4):** `workspace_write_file`, `workspace_save_dialog`,
  `workspace_open_dialog`, `workspace_set_dirty`. Each wraps a *distinct* native
  capability (atomic write; save dialog; open dialog; dirty mirror for the quit
  guard). They cannot be dropped: the trusted webview is denied direct plugin
  invocation by the issue-034 ACL posture, so each native action needs its own
  app command and its own grant. They *could* be merged to 2–3 behind
  `mode`/`op`, but that widens each ACL grant and is a behavior change, not a
  rename — **not recommended.**
- **Project (2):** `project_pick_folder`, `project_read`. Folder selection vs.
  bounded recursive read + `Content/` discovery are separate operations with
  different argument/return shapes.
- **First-run warning (2):** `first_run_check_acknowledgement`,
  `first_run_write_acknowledgement`. Required by ADR 0003's mandated disclosure
  of the non-yielding limitation; read vs. atomic write of the acknowledgement
  store.

Nothing structurally forces a ninth product command. The 70 proof commands and 4
dead commands are **not** product surface — they exist only to drive packaged
proofs and, after Stage 6, exist **only** in the `--features proof-harness`
binary. The proof harness will legitimately carry ~74 commands, but that is the
*proof* build's surface, explicitly permitted by the plan ("proof commands may
exist only in the explicit proof build"), and is not counted against the
eight-command PRODUCT target.

## Implementation status — slice 6 (native binary/runtime command-inventory enforcement)

This section records slice 6: the standalone compiled-artifact command-inventory

### The checker

`scripts/check-binary-command-inventory.mjs` — a cross-platform, dependency-free
Node checker (pure-Node printable-ASCII string extraction; no system `strings`,
`nm`, or `plutil`, so the same check runs on the macOS/Windows/Linux CI legs).

**Inventory derivation (no duplicative drift).** The checker parses
`build.rs` for `HANDLER_ORDER` (78), `PRODUCT_COMMANDS` (8), and `PROOF_COMMANDS`
(70) and asserts, every run: the exact counts (8 / 70 / 78), that product and
proof are **disjoint**, and that `product ∪ proof == HANDLER_ORDER`. It never
carries a second copy of any command list — the Rust source of truth is the only
inventory. A drifted build.rs fails the derivation before any scan.

**Modes / paths.**
- `product` — resolves the `MonoGame Playground.app` bundle (identifier
  `com.monogame.playground`) under `target[/<triple>]/release/bundle/macos`, or an
  explicit `--bundle`/`--binary`. Scans the embedded executable **and** the staged
  product `dist/`.
- `proof` — resolves the `MonoGame Playground Proof.app` bundle (identifier
  `com.monogame.playground.proof`), scans its executable **and** `dist-proof/`.
- Options: `--bundle`, `--binary`, `--frontend-dist`, `--target <triple>`,
  `--allow-shared-binary`, `--self-test`.

**Profile identity / anti stale-or-wrong-profile.** The shared
`target/release/monogame-playground` path is overwritten by whichever profile
built last, so it cannot self-identify. The checker resolves the mode-correct
`.app` by name and verifies its `CFBundleIdentifier` matches the mode; a
mismatched identifier is refused ("wrong-profile artifact"). It also refuses to
guess against the shared release binary unless `--allow-shared-binary` is passed.
The staged-dist scan additionally verifies `profile-manifest.json` `profile`
matches the mode, so a stale/foreign dist is rejected.

**PRODUCT checks (non-vacuous).** Positive floor (must be present, so an
empty/failed read fails loudly): all **8** responsibility-named product commands
